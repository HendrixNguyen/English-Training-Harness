## Binding producer interfaces and decisions

1. Shared Task DTO adds `content_origin:'generated'|'legacy'|'outline'`, nullable `content_revision:string` and nullable `quiz_result`. Revision is an opaque server SHA-256 fingerprint of task type plus canonicalized actual content; ignore title/time/completion/result and key-order-only JSON differences. Exercise GET and daily use one mapping helper. Frontend retains server origin/revision; a schema marker alone is insufficient trust.
2. Generated schema1 content is revalidated on hydration and grading. New generation persists `content_level` with its actual level; saved content validation uses that level, never a later changed learner level. Historical schema1 without level uses documented union-of-supported-level passage bounds while retaining generated shape/count and degeneracy rules; do not globally regenerate valid saved exercises. Invalid schema1 returns409 `exercise_content_invalid` without provider calls.
3. Unmarked nested roadmap drafts always hydrate unless they are a complete valid legacy quiz. Define legacy precisely: recognized preexisting root-level passage/word/question shapes, explicit persisted `content_origin:'legacy'`, or complete nested questions with unique nonblank IDs/prompts, at least two distinct options with A–D keys, and consistent optional keys/explanations. Generated minimum counts apply only to generated content. An unmarked nested passage-only/word-only body is an outline; an explicitly marked or recognized flattened legacy reading/word list may have zero questions and stays usable/ungraded. No one-option/placeholder question qualifies. Mixed vocabulary retains words/examples/questions. Do not retroactively tag ambiguous drafts as legacy merely to skip generation. Test/document each recognized shape.
4. Repair is explicit authenticated GET `/api/v1/quests/exercises/:id?repair=true`, only for an owned active, available, incomplete task whose stored schema1 is invalid. Rate-limit it, use at most existing two malformed-output attempts, and CAS against the original content snapshot plus ownership/active/incomplete conditions. Failed repair leaves bytes intact. Lost CAS rereads/validates a concurrent winner once, with no generation loop. Completed saved results are never repaired/overwritten. Ordinary valid cached reads make no AI calls. Old module focus may fall back to module title when briefing; preserve actual profile/module/day mapping.
5. POST `/api/v1/quests/progress` body is `{exercise_id,duration_seconds,content_revision?,user_answers?:{[question_id]:option_key}}`. Decode one bounded JSON object strictly: known fields, no duplicate keys/trailing tokens, string choices; reject client score/key/correctness fields. Supplied answers have no unknown IDs and use an existing option. New UI ALWAYS supplies server revision and, for tasks with questions, exactly one answer per required ID; revised requests require completeness, while zero-question tasks accept empty/missing answers. Supplied revision must match current owned stored content; mismatch→409 `exercise_content_changed`. Controller rolling-release ruling: absent revision preserves older callers' time/completion compatibility, allows partial/no answers, and persists supplied valid choices explicitly UNGRADED even when keys exist. Never silently grade against possibly changed content. Malformed/unknown-ID/invalid-option data still400 before any write. Existing completed quiz_result is never overwritten by revisionless time-only/partial requests. No generation during POST.
6. Validate request, ownership/current-day/active-roadmap, supplied-answer shape/options, revision and revised-request completeness before any write. For revised learning requests also validate current stored generated content; invalid→409 `exercise_content_invalid`. Revisionless old time-only requests retain the existing compatible completion path and do not trigger AI/content repair; malformed supplied answers still fail before writes. Preserve indistinguishable404 `exercise_not_found` for foreign/inactive/future/invalid IDs; bad answers→400 `invalid_request`. Server grades from persisted keys/explanations only with matching supplied revision, never client score. Pure grading returns `quiz_result:{status:'graded'|'ungraded',answered_count,question_count,correct_count:number|null,score_percent:number|null,duration_seconds:number,answers:[{question_id,selected_option,correct_option:string|null,is_correct:boolean|null,explanation:string|null}]}` in question order. Matching revision, all questions keyed and Q>0→graded, percentage `round(100*correct_count/Q)`; revisionless, legacy keyless or zero questions→ungraded aggregate nulls. Revisionless answers have correct_option/is_correct/explanation null regardless of stored key; counts honestly reflect supplied valid selections. Other unknown per-answer fields are null, zero-question answers `[]`. Store duration_seconds as the server-clamped seconds of this successful completion attempt, not the daily total or task target; saved-summary time survives timer cleanup/reload and never determines the score. Historical null result means unknown per-task saved duration, never fabricated0. No fabricated0%/100%; no mastery/reward effect. Historical completed rows have null result until actual answers are recorded; never invent history.
7. Add nullable `exercises.quiz_result JSONB` in migration0005 (latest inspected0004_rls; recheck before writing). Extend quests-owned read/write interfaces and all scanners, not another module's tables. At existing MarkComplete step persist result and `is_completed=TRUE` atomically, scoped to owned roadmap and expected content revision; never attach captured answers to a replacement revision. Retain an existing completed result rather than replacing it with another selection set. POST adds `quiz_result`; daily/exercise Task returns same stored result. Standard Redis increment→daily upsert→pet hook/target flag→MarkComplete ordering, wall-clock anchors, caps, day/time semantics and hook-failure behavior remain intact.
8. Durable result storage is not global exactly-once time credit: Redis/Postgres/pet remain separate. UI permits one in-flight save, retains answers and attempted duration on failure, and refetches daily before retry after an ambiguous outcome. Matching completed revision/result ends reconciliation without another POST; confirmed incomplete permits explicit retry; unknown outcome offers read-only checking. Existing time credited before a failed completion write can still require manual reconciliation; document that limitation without a tracking redesign. Completed reopen uses authoritative stored result and never posts.
